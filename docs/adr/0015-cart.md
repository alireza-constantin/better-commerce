# ADR-0015 — Persistent Cart Ownership, Merge, and Concurrency

Status: Accepted
Date: 2026-07-28
Accepted: 2026-07-28
Frozen: 2026-07-28

## Context

The storefront needs a Cart that works before and after login without turning
browser storage, Redis, Catalog, Pricing, Inventory, or Orders into competing
sources of truth.

ADR-0004 defines Cart as mutable purchase intent. It is not authoritative for
price, stock, tax, fulfillment eligibility, or accepted purchase history.
ADR-0008 also forbids Cart from reserving Inventory. This ADR decides the
remaining initial questions: persistence, anonymous and authenticated
ownership, login merge, expiry, concurrency, checkout handoff, and storefront
coordination.

The platform is deployed once per merchant with a separate database and Redis
instance. Cart therefore needs no tenant discriminator. The design should
remain reliable for a small store without introducing distributed caches,
queues, or event-driven coordination.

## Decision

Cart is one API business module and the sole authority over Cart and Cart-line
persistent data.

Cart state is stored in PostgreSQL. Redis remains an authentication-session
store and is not durable Cart storage. A Redis restart may invalidate a login
session but must not delete a customer's Cart.

Version 1 supports:

- anonymous carts before login;
- one active cart per authenticated customer;
- explicit anonymous-cart claim and merge after login;
- integer quantities for purchasable Variants;
- optimistic concurrency through a Cart version;
- login-required checkout;
- deterministic expiry and closure.

Guest checkout is not enabled. An anonymous visitor may build a Cart, but must
create an account or log in before submitting an Order.

## Module ownership

Cart owns:

- Cart identity, ownership, lifecycle, and version;
- Cart lines and requested quantities;
- anonymous Cart access-token hashes;
- merge and claim rules;
- Cart expiry and closure;
- mutation limits and concurrency conflicts.

Cart does not own or mutate:

- Product or Variant lifecycle;
- current prices, promotions, tax, or rounding;
- Inventory quantities or reservations;
- Shipping methods or quotes;
- Payment records;
- Orders or Order snapshots;
- customer credentials or sessions.

Cart calls narrow public contracts from Catalog when it must validate a
Variant. Read projections may compose Catalog, Pricing, and Inventory facts,
but those facts are not persisted as Cart authority.

No module may update Cart tables directly. Checkout uses Cart's public contract
and Cart closes itself through a named operation in the checkout transaction.

## Persistent model

A Cart has:

- an opaque UUID;
- lifecycle status: `active`, `checked_out`, `merged`, or `expired`;
- nullable authenticated customer ID;
- nullable anonymous access-token digest;
- positive monotonic integer version;
- UTC creation and last-mutation instants;
- UTC expiry instant;
- nullable terminal instant;
- nullable successor Cart ID for a merged Cart.

A Cart line has:

- an opaque UUID;
- Cart ID;
- Variant ID;
- positive integer requested quantity;
- UTC creation and update instants.

Version 1 does not accept arbitrary customer configuration on a Cart line.
Catalog Variant selection already represents the concrete purchasable unit.
Engraving, uploaded files, service answers, measurements, and other custom line
configuration require a focused contract defining validation, normalization,
size limits, privacy, and Order snapshots.

The database enforces at most one active Cart for an authenticated customer.
Line uniqueness is `(cart_id, variant_id)` in version 1.

## Anonymous ownership

The API issues a cryptographically random anonymous Cart token with at least
256 bits of entropy when the first Cart mutation needs one. The raw token is
stored only in an HttpOnly cookie and is never stored in the database, returned
in JSON, exposed to JavaScript, placed in a URL, or written to logs.

The database stores a keyed digest of the token. Token comparison uses the
digest, and the key comes from deployment secrets rather than the database.

The cookie is:

- `Secure` in production;
- `HttpOnly`;
- `SameSite=Lax`;
- scoped to the API's Cart path where deployment routing permits;
- persistent only for the configured anonymous Cart lifetime.

The existing origin and CSRF controls apply to every state-changing Cart
request. Possession of the anonymous cookie is necessary but not sufficient
for a cross-site mutation.

Anonymous Cart tokens are bearer credentials. Responses and logs must never
disclose whether another token or customer owns a Cart. Ownership mismatches
return `404`.

## Authenticated ownership

An authenticated request resolves the customer's one active Cart. Logging out
does not copy that Cart into a new anonymous Cart and does not delete it. A
later login by the same customer restores it until it expires.

Cart ownership is per customer account, not per device. Multiple devices see
the same authenticated Cart and coordinate through its version. This gives the
customer continuity while preventing divergent server-side carts for the same
account.

## Claim and merge after login

Authentication does not mutate Cart tables and Cart does not participate
inside the credential-verification transaction.

After a successful login or registration, storefront-core explicitly calls an
authenticated Cart claim operation. The operation receives ownership from the
authenticated session and the anonymous Cart cookie; it never accepts a
customer ID or anonymous token in a JSON body.

Claim behavior is:

1. If no anonymous Cart exists, return the customer's active Cart or an empty
   Cart representation.
2. If the customer has no active Cart, transfer the anonymous Cart to that
   customer and rotate away the anonymous credential.
3. If both Carts exist, merge them in one PostgreSQL transaction.
4. Equal Variant lines are combined by adding requested quantities.
5. Distinct Variant lines are preserved.
6. If the result violates quantity or line limits, reject the merge atomically
   with a typed conflict. Neither Cart is modified.
7. On success, the anonymous Cart becomes `merged`, points to the surviving
   customer Cart, and can no longer be mutated anonymously.

Claim is safely replayable. A repeated request using the consumed anonymous
credential by the same authenticated customer returns the surviving Cart
without merging quantities twice. A consumed credential cannot be claimed by
another customer.

Login remains successful if Cart claim fails. Storefront-core exposes the
typed Cart conflict so presentation can explain the problem and let the
customer resolve it. It must not silently discard either Cart.

## Mutation and optimistic concurrency

Every successful logical Cart mutation increments `version` exactly once and
returns the complete current Cart representation.

Every update, removal, clear, claim, and checkout handoff supplies the version
the caller observed. A stale version returns `409` with stable problem type
`cart.version_conflict` and the current version. The client refetches and asks
the user to repeat conflicting intent; it does not automatically replay a
mutation against newer state.

Line quantity changes are absolute desired quantities, not unbounded
increment/decrement commands. Setting a line quantity to zero is represented
by the explicit remove operation. This keeps retries understandable and avoids
accidental double increments.

Mutation requests use `Idempotency-Key` where an uncertain network result could
otherwise repeat a non-idempotent command, especially claim and clear. The
server binds a key to the owner, operation, and canonical request fingerprint.
Reusing a key with different input is rejected.

The initial limits are deployment-validated and bounded:

- maximum 100 distinct lines per Cart;
- quantity from 1 through 999 per line;
- maximum 100 mutation requests per authenticated or anonymous Cart per
  minute, enforced by the existing API rate-limiting boundary when introduced.

The database remains the concurrency authority. In-process locks and Redis
locks are not used for Cart correctness.

## Read representation

The persisted Cart records only intent. A Cart response may enrich each line
with current:

- Product and Variant display information;
- exact price projection;
- Inventory availability;
- a stable availability or invalidity reason.

Unavailable, unpublished, deleted, or unpriced lines remain visible so the
customer can understand and remove them. Their current invalid state does not
rewrite the stored intent. Presentation strings remain Persian and
storefront-owned; the API returns stable machine-readable reason codes and
safe facts.

A Cart total is an advisory current projection. It is not an Order quote and
must be labelled and treated as recalculable.

## Expiry and cleanup

Cart expiry is based on the last successful mutation, not reads. Reads do not
extend lifetime or cause database writes.

Initial defaults are:

- anonymous active Cart: 30 days after its last mutation;
- authenticated active Cart: 90 days after its last mutation;
- merged-token replay metadata: 24 hours after successful claim.

These durations are validated deployment configuration. Expired Carts are
terminal and never reopen. The next mutation creates a new active Cart.

Correctness uses expiry checks inside Cart commands. A bounded background job
may mark old Carts expired and later purge terminal Cart data according to the
store's retention policy, but the job is not required for correct ownership or
checkout behavior.

## Checkout handoff

Checkout requires an authenticated customer and accepts a Cart ID plus the
observed Cart version, delivery input, selected Shipping method, Payment
method, and checkout `Idempotency-Key`.

Inside the existing PostgreSQL checkout transaction:

1. Cart locks and validates the customer's active Cart and expected version.
2. Checkout reads the exact Variant IDs and quantities from Cart.
3. Catalog, Pricing, Shipping, and Inventory revalidate current authority.
4. Orders and Payments create their records and Inventory reserves stock.
5. Cart transitions to `checked_out`.
6. The transaction commits or every change rolls back.

The browser does not submit authoritative line prices or duplicate the Cart
lines as checkout truth. A stale Cart version, invalid line, changed price,
insufficient stock, or unavailable Shipping rule rejects checkout without
closing or partially changing the Cart.

An idempotent replay of a successful checkout returns the same Order even
though the Cart is already closed. A new Cart is created only by a later Cart
mutation.

## Public platform contract

The initial external contract provides operations conceptually equivalent to:

- get current Cart;
- set the absolute quantity for a Variant;
- remove a line;
- clear the Cart;
- claim/merge the anonymous Cart after authentication;
- submit checkout from an authenticated Cart.

Exact HTTP paths and DTO names belong to the external HTTP contract, OpenAPI,
and generated SDK. Nest providers, repositories, entities, token digests, and
transaction implementation are private.

`@better-commerce/storefront-core/browser` owns:

- credentialed Cart requests;
- CSRF lifecycle;
- session-triggered claim coordination;
- current Cart state subscriptions;
- stale-version and merge-conflict normalization;
- checkout idempotency and uncertain-result handling.

It does not own Cart persistence or silently resolve business conflicts.
Framework adapters may expose the state through React, Astro, TanStack Start,
or another renderer without changing the protocol.

## Failure behavior

The API uses stable problem types, including:

- `cart.not_found`;
- `cart.version_conflict`;
- `cart.limit_exceeded`;
- `cart.line_invalid`;
- `cart.merge_conflict`;
- `cart.checkout_requires_authentication`.

User-facing text is Persian. Diagnostic metadata is safe, bounded, and never
contains raw tokens, session IDs, secrets, or another customer's identifiers.

## Non-goals

Version 1 does not include:

- guest checkout;
- Inventory reservation while items are in a Cart;
- saved-for-later lists or wishlists;
- multiple named Carts per customer;
- shared, collaborative, or merchant-edited Carts;
- promotions, coupons, tax, or Shipping selection persisted in Cart;
- abandoned-Cart marketing or Admin browsing;
- cross-device anonymous Cart synchronization;
- arbitrary custom line configuration;
- Redis Cart caching;
- event publication for ordinary Cart mutations;
- real-time push synchronization between devices.

## Consequences

The design adds a durable Cart table set, an anonymous bearer cookie, expiry
handling, and optimistic-concurrency behavior. It also requires storefronts to
surface merge and stale-version conflicts instead of hiding them.

In return, Cart survives process and Redis restarts, authenticated customers
receive one consistent cross-device Cart, anonymous visitors can prepare a
purchase before login, and checkout never trusts stale browser prices or stock.
The Cart remains independently replaceable because other modules interact only
through its public contract.

## Rejected alternatives

### Store the Cart only in localStorage

Rejected because browser state cannot provide authoritative ownership,
cross-device continuity, safe checkout handoff, or centralized protocol fixes.

### Store the Cart in Redis

Rejected because Cart is durable customer intent and Redis is currently an
authentication-session dependency, not the system of record. Correctness
should not depend on cache persistence configuration.

### Reserve Inventory when adding to Cart

Rejected by ADR-0008 because abandoned Carts would hold stock and availability
would become dependent on Cart cleanup.

### Merge inside the login transaction

Rejected because Authentication would acquire Cart persistence responsibility
and Cart failure could incorrectly fail credential login.

### Let the browser choose which Cart wins

Rejected as the default because it can silently discard intent and produces
different results across storefront implementations.

### Last-write-wins without versions

Rejected because multiple tabs and devices could silently overwrite quantities
or resurrect removed lines.

## Invariants

1. Cart alone mutates Cart and Cart-line persistence.
2. PostgreSQL is the Cart system of record; Redis is not.
3. Cart stores purchase intent, never authoritative price or stock.
4. Adding to Cart never reserves Inventory.
5. Anonymous raw Cart tokens never enter the database, JSON, URLs, or logs.
6. Checkout requires authentication in version 1.
7. Claim/merge is atomic, deterministic, replay-safe, and never silently drops
   intent.
8. Authenticated ownership is one active Cart per customer across devices.
9. Every logical mutation uses optimistic version concurrency.
10. Stale mutations are rejected rather than automatically replayed.
11. Checkout revalidates all authoritative commerce facts.
12. Successful checkout and Cart closure commit in the same transaction.
13. Reads do not extend Cart expiry.
14. Expired and terminal Carts never reopen.
15. Public consumers depend on HTTP/OpenAPI/SDK/storefront-core contracts, not
    API internals.
